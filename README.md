# Paolla

Статичний застосунок складу й виробництва. `index.html` містить інтерфейс, `data-integrity.js` — правила збереження та складських рухів. Збирання не потрібне: обидва файли публікуються разом через GitHub Pages.

## Перевірка

Потрібен Node.js 20 або новіший. Залежностей для тестів немає.

```sh
npm test
```

Тести виконують реальні скрипти застосунку в порядку завантаження. DOM, авторизація, сховище та відповіді Supabase імітуються; запити до робочої бази заборонені тестовим оточенням. Вони перевіряють відмову запису та читання, повтор після невизначеної відповіді, одночасні сесії, резерви, проведення, старі документи, наряди, звіти й друк. Це не перевірка реальних політик Supabase або повний браузерний тест.

## Збереження

- Новий знімок створюється через `insert`; наявний змінюється через `update` з атомарним фільтром за попереднім `modified_at` та `warehouse_id`.
- Сервер має повернути збережений рядок. Помилка, нуль оновлених рядків або непідтверджений вміст не вважаються успіхом. `created_at` при оновленні не змінюється.
- Після відмови відновлюється останній підтверджений стан. Поля форми залишаються доступними для виправлення й повтору. Незавантажений склад не можна перезаписати.
- Після втрати відповіді застосунок перечитує знімок. Якщо запис уже відбувся, складський рух не повторюється. Якщо підтвердження поки немає, наступне натискання спершу з’ясовує результат попереднього запиту.
- Зміни в одній вкладці серіалізовані: під час запису інші дії заблоковані. Стара версія іншої вкладки одержує конфлікт; введені значення потрібно переглянути перед повтором.

Використовуються вже наявні поля `warehouse_snapshots.warehouse_id`, `payload`, `modified_at`, `created_at`. Потрібна унікальність `warehouse_id`, а також дозволи SELECT/INSERT/UPDATE відповідно до ролі. Реальна схема й RLS не входять до цього репозиторію; їх потрібно перевірити перед публікацією. Запит `update` з фільтром і поверненням рядка відповідає [Supabase JavaScript API](https://supabase.com/docs/reference/javascript/update).

**Після оновлення всі користувачі мають перезавантажити відкриті вкладки.** Старий клієнт із безумовним `upsert` не дотримується нового протоколу. Для обов’язкового захисту від старих або сторонніх клієнтів потрібне окреме серверне правило чи RPC; наявні серверні політики це виправлення не змінює.

## Складські правила

- Резерв не змінює фізичний залишок; його видалення також не змінює залишок.
- Проведений видаток можна повернути в резерв кнопкою **«Скасувати проведення»**: кількість повертається на склад один раз.
- Редагування документа застосовує різницю нового й попереднього руху для кожного товару. Від’ємні залишки дозволені.
- Старі документи з полями `quantity`/`product_id` підтримуються поряд із `items[]`. Історичний видаток без статусу вважається проведеним — відповідно до поведінки початкового формату. Перед випуском це правило потрібно звірити з історичними даними.
- Наряд зберігає `product_id`. При завантаженні старий наряд пов’язується з товаром лише за єдиним точним збігом назви. Невизначені відповідності не приймаються на склад; товар потрібно обрати вручну в неприйнятому наряді.
- Прийняття зберігає точний рух у `received_stock`. Скасування використовує саме цей товар і кількість. Для старих прийнятих нарядів без руху використовується їхня збережена кількість; попередні помилкові зміни потребують звірки з первинними документами.
- Перед зміною або видаленням прийнятого наряду потрібно скасувати прийняття. Виконання цехів також захищене після прийняття.
- Товар із залишком або історією можна архівувати; фізичне видалення заблоковане.

## Випуск

1. Зберегти резервну копію поточного знімка та перевірити відновлення в тестовому середовищі.
2. Звірити унікальність `warehouse_id`, політики та правила історичних документів; перевірити одночасні запити двох сесій на окремому складі.
3. Публікувати `index.html` і `data-integrity.js` в одному коміті; перезавантажити всі клієнти.
4. На тестовому складі перевірити створення, резервування, проведення, скасування, редагування наряду та повторне завантаження.

Виправлення запобігає новим помилкам. Воно не перераховує наявні робочі залишки автоматично: наслідки старих подвійних списань або видалених резервів потрібно звірити окремо.
